Overview

A UR3 on a 1.5-meter-long linear rail picks up a coke can from a randomly generated location on a green plate and places it on a blue plate on the other side of the rail. Every run has the following steps play out (as is depicted in the flowchart):

  1. The arm looks down from a fixed position, allowing the wrist mounted camera to look 0.6m above the spawn area.
  2. The RGB-D camera finds the red can (the centroid red pixel), and reads its depth, sensing it and turning that data into an xyz position.
  3. The Kalman filter estimates the can position by utilizing 20 photographs, using uncertainties defined in the code to work out its position.
  4. The rail drives the UR3 towards the can to line up with it, using the rail Kalman filter and an LQR.
  5. The PBVS moves the gripper closer to the can, until it is 0.15m above the can, constantly taking photos and updating the filter each movement.
  6. The arm grabs and lifts the can, swings it over the rail and then back down onto the blue plate.

Each joint in the robot throughout this process is driven using LQR and has gravity compensation, using joint angles and speeds estimated by observers, which have noise. No controller in this simulator uses the true positions in code, but the true joint positions are used to compare the robots estimations to for the purposes of this report.

Modelling - All

This section is brief, as most of the individual sections explain how all the code for each section interacts with each other, but some parts of the project are integral to all parts and will be explained below:

Joints

  • State: Uses the angle and the speed. Gets given the motor torque, and the sensor utilizes an encoder, which is only able to read angles.
  • Physics: Newtons to work out spinning forces. The formula for the torque is angular acceleration multiplied by the inertia.
  • Matrices: A matrix [[0, 1], [0, 0]] works out what happens with no motor push (the angle changes by the speed, and the speed stays the same). B matrix [[0], [1/J]] figures out what the motor does as it changes the speed (a heavier joint speeds up less). C matrix [1, 0] defines what the sensor can see (angle but not speed).
  • Assumptions: No friction, gravity is handled separately (Mujoco simulates it, and the controller cancels it with an extra torque worked out at the estimated joint angles), and each joint is worked out completely independently, even though in reality they’d affect each other.
  • Content used: The Week 8 tutorial’s DC motor position servo model (same A, B, C shape, with our own J values swapped in from the MuJoCo UR3 model), and the Week 5 tutorial for the rank checks.

Rail Model

  • State: Uses the position and the speed of the base along the rail. Gets given the motor force, and the sensor utilizes an encoder, which is only able to read position.
  • Physics: uses F=MA with rail friction. The mass is 10.7 kg (the base and the arm together), the friction (damping) is 100 N/m/s, and has 2ms steps.
  • Matrices: A matrix [[1, 0.002], [0, 0.981]] works out what happens with no motor push (the position moves by speed × 0.002 s, and the speed drops a little bit each step because of friction). B matrix [[0], [0.00019]] figures out what the motor does as it changes the speed (it’s tiny because the base is heavy and each step is really short). C matrix [1, 0] defines what the sensor can see (position but not speed).
  • Assumptions: The arm swinging around pushes the base a bit, but that isn’t in the model, so we cover it with the doubt (Q) in the rail Kalman filter instead.
  • Content Used: The Week 7 tutorial’s cart model (position and speed with damping, made into 2 ms steps), with our own mass and damping values from the MuJoCo scene.

Rank checks

  • What it does: Checks that the motor can change in both angle and speed for the joints and position and speed for the rail. The observability checks both states can be figure out based upon the sensor, even though (as seen later) the speed is not measured directly.
  • Results: Passed both the joints and rail.
  • Content used: Week 5 tutorial (ctrb and obsv).

Sensing - James

Camera calibration

The pinhole camera intrinsics K were found by rendering 14 camera views of a checkboard approximatly 0.45-0.65 m away at these varied distances as well as varying tilt +/- 30 degrees alongside distance inside the MuJoCo simulation then calibrated with the Machine Vision Toolbox (CameraCalibration.py). Through this process K is found in each of the 14 images using (Central.Camera.images2C). The focal length is just under 500 px. Mean reprojection error: 0.18 px.

Noise models

Noise sourceModel
Pixel positionGaussian, σ = 1 px
Depthσ(Z) = 0.0015 + 0.0022 Z² m, growing with distance
Joint encodersGaussian, variance 1e-5 rad²
Rail encoderGaussian, σ = 2 mm
Centroid bias3 mm, added to the filter’s R rather than averaged away

Depth noise grows with distance, so the PBVS target hovers 15 cm above the can this allows for a balance of 2 variables where depth is more accurate enough while keeping the can in view.

Frames: from pixel to the quantity the controller acts on

  1. Pixel (u, v) and depth Z from the wrist camera.
  2. Camera frame, computer-vision convention: PC = Z · K-1[u, v, 1]T.
  3. Axis flip by [1, −1, −1] to the MuJoCo camera convention (camera looks along −z).
  4. World frame: PW = pcam + Rcam PC.
  5. Subtract the can height (0.135 m) to get the can base, which is the PBVS target.

The rail position shifts the robot base within the world frame, so the rail estimate affects the whole chain.

Estimation - Jack

Can Kalman Filter

What it does: takes the camera’s x y z readings and combines 20 photos to estimate the can’s position, then keeps refining that estimate with new photos as the gripper approaches, since closer photos are more accurate.

How: it finds the center of the red pixels (u,v) and the depth (z). The inverse of the camera matrix lets you work out where the point is relative to the camera, and the camera pose (estimated from the rail and joint content), works it out as a xyz world point. Each photo predicts the movement of the can as it moves closer and then corrects itself depending on how accurate the estimate was depending on the estimation.

Locations: Starts in the middle of the platform where the objects spawn, and is defined by being unsure by 20cm2, the area in which the cans can spawn.

Camera noise function ( R ): Is the pixel noise (estimated to be 1 px, about 0.9 mm at 0.45 m, picked by us), the depth noise (estimated to be 1.5 mm + 2.2 mm·Z², about 1.9 mm at 0.45 m, from the Week 4 depth camera model), and the 3mm error (estimated from a test run where the filter finished 2.7 mm off, caused by the red-pixel centre not being exactly the centre of the can top).

The doubt (Q): Is 2mm. This is because the can doesn’t move, so Q could be 0, but then the filter would become too sure and stop listening to new photos. A small Q keeps it updating (Week 7: when in doubt, make Q bigger).

Consistency check (NEES): for a 3-state filter the mean NEES should be near 3, and about 95% of trials should fall below 7.815. Values above this mean the filter is over-confident (its covariance is too small). [Add your NEES result here.]

Rail Kalman Filter

Why?: We added this in after feedback because the Ur3 was basically fixed on the rail, which both made it so the estimated states were the can position and joint speeds, and that the rail practically did nothing but just move the UR3 into a single position. After we got feedback, we decided to make the rail a moving joint with a motor and a noisy encoder, so we added this filter so that it drives up to the can using only an estimated position.

What it does: Takes the noisy rail encoder reading and estimates the base position and speed based off of that. Speed is not measured, the filter works out how much the position changes and estimates it off that. The rail LQR then drives the base to line up with the can using estimates.

Location in code: All main content is in make_rail_model() in RailEstimation.py. The filter works in UR3_move_joints_lqr() in LQRPart.py, and uses kf_step() from RailEstimation.py.

Content Used: This part used the week 7 Kalman filter stuff (based off the cart model which was helpful since its actually kind of similar in terms of movement in terms of kf_step) and the Week 6 LQR content (the part used in the rail controller).

Joint observer

Each joint runs a copy of its model and corrects it with the encoder: x̂̇ = A x̂ + B u + L (y − C x̂). The gain L is the steady-state Kalman gain from lqe with process noise Q = diag(1e-3, 1) and measurement noise R = 1e-5. Larger Q/R makes the estimate faster and noisier. Smaller Q/R makes it smoother and slower. [State how you checked or tuned these values, e.g. the sweep in the results.]

What we found

Can Kalman Filter: The filter was really overconfident at the start, with it thinking that it was 0.65mm out when it was 3.6mm. After working out that the average of the photos stopped it from giving random noise errors but not accounting for steady continuous errors, the 3mm was added to R, which matched up with the 2-3mm it was actually off by in the other runs.

Can position is important: The error was bigger (around 6 to 8 mm more) when it was at the edge of the 20 pictures at the start, probably because it shifted the red pixel center because it didn’t get a flat down top view.

Rail Kalman Filter: It averages a 0.8mm error but had a pretty accurate 98% range of result, so realistically it was pretty accurate and honest with how sure it was about being accurate.

Disturbance: We added a 5N push when it approached the can. Every time the robot recovered and still worked out where the can was and placed it. Within about 5mm accuracy.

Control - Will

All three controllers act on estimated states. We use LQR for the six arm joints, LQR for the rail and a Position Based Visual Servo (PBVS) that decides where the arm should go. For every step the controllers update (2ms)

Joint LQR

What it does: Joint LQR determines the amount of torque each joint should use to reach its target angle. It uses the speed and angle estimation by the joint observer as opposed to real values.

How: LQR balances our rating of how far away we want to be from target (Q) and our setting of how limited we want to adjust torque (R). Torque = −K×(estimated state − target) where we set target speed at 0. It can be thought of as the spring or force that pulls the joint to the target (K1) plus a damper that prevents it moving too fast (K2).

Weights: We found that the combination of Q = diag(100, 1) & R = 1. We penalise the angle error 100x more than the speed meaning the controller favours reaching the target. We used a double integrator model which makes the angle gain 10 for each joint, and speed gain depends on the joint inertia. For a double integrator this gives K1 = √(Q11/R) = 10 N·m/rad for every joint, while K2 = √(1 + 20J) depends on the joint inertia J. The benefit is heavy joints move slowly and each joint is well damped since it doesn’t drop below 0.71.

Why: The weight we’ve chosen given reasonably settles with arm’s joints without exceeding the motor torque limits. Raising Q increased noise in the torque since the estimate speed noise passes through K2 which is why we stopped at 100.

Gravity Feed-Forward

What it does: Gravity Feed Forward stops the arm sagging from its weight so LQR only deals with residual error.

How: Because our joint model has no gravity each step we copy the arm’s estimated joint angles into another MuJoCo data object and determines what torque is required at that pose to overcome gravity which is then added to the LQR output.

Why: Our joint model has no gravity term and without it we would have a steady-state error. With K1 = 10 a 5 N.m gravity torque would leave a 0.5 rad offset. Feed forward uses the known model, adds no state and leaves feedback to correct model error.

Rail LQR

What it does: This is used for the rail that the UR3 sits on from our IR assignment. It moves the base of the UR3 along the rail using the speed and position from a Kalman filter.

How: It is a discrete LQR with weights diag(1000,1) & R = 0.01. The position error here we penalise more than the joints and a reduced R value since the rail requires a lot of force to move. The output force is limited at 200N. The Rail target is the estimated can position converted to a rail position.

Position Based Visual Servoing (PBVS)

What it does: Moves the gripper above the can using the Kalman Filter’s estimate, then down to pick it up. “Position Based” is where the error is worked out in 3D from the estimated can position, instead of from pixel errors in the image.

How: For each step we find two errors; Distance to target & Angle distance to being vertical. We scale them by a gain λ = 2 to get the desired end effector velocity. The Jacobian allows us to turn joint speeds into end effector speed at the current pose, the code uses its pseudo-inverse to turn desired velocity into joint speeds then moves the joints for 0.2 s and takes another photo. We repeat this process until the position error is under 2mm. The target is 0.15 m above the can for the approach then 0.01 m above the can to grab.

Why: We use PBVS instead of image based because the calibrated RGB-D camera gives 3D position it’s simpler to gain error. We use a closed loop rephotographing every move for more accuracy in the filter. The 0.15 height allows camera to remain in view with improved accuracy.

How to Run

These steps assume Windows with PowerShell, as used in our setup. You need Git and Python installed first.

  1. Download: 
    git clone https://github.com/Hefferss/BartendingRobotSensors
cd BartendingRobotSensors
    If you don’t use Git, click Code, then Download ZIP on the GitHub page, unzip it, and open a terminal in that folder. Run every later command from inside the project folder.
  2. Set up Python (if you haven’t already): 
    python -m venv .venv
.venv\Scripts\activate
    The first line creates a private environment for the project’s packages and the second switches it on. You should see (.venv) at the start of the terminal line. If PowerShell refuses to run the activate script, run Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned and then activate again.
  3. Install the packages: 
    pip install mujoco numpy control matplotlib
    Do this with the environment active. If a later run stops with ModuleNotFoundError: No module named 'x', install that package with pip install x.
  4. Run the demo by playing MainRunFileMujoco.py: 
    python MainRunFileMujoco.py
    You can also open the file in VS Code and press the play button, as long as the selected Python interpreter is the .venv one.
  5. Simulate a disturbance: use push_on = True in MainRunFileMujoco.py to simulate a 5N push. Open the file, set push_on to True, save, and run it again. Set it back to False for a normal run.

What you should see

  1. A MuJoCo viewer opens with the UR3 on its rail and a randomly placed can, and a separate window shows the camera image. If the terminal waits for input, press Enter to continue.
  2. The arm moves to its look pose and takes 20 photos. The terminal prints the Kalman filter’s can estimate, its uncertainty and the error against the true position.
  3. The base slides along the rail to line up with the can, then the gripper steps down in small moves until it is 0.15 m above the can, updating the estimate after every photo.
  4. The arm grasps and lifts the can, swings it over the rail and places it on the blue plate.
  5. The viewer stays open at the end. Close it to finish the run, after which the rail estimate plot appears.

CameraCalibration.py needs two more packages (pip install opencv-python machinevision-toolbox-python) and reproduces the camera calibration. graphs.py regenerates the result figures from the saved files in the results folder.
